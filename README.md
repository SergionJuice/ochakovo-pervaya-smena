# «Первая смена» — исходники для GitHub

Исходный проект игры «Первая смена» для «Очаково»: Рита, три задания в любом порядке, компактная карта предприятия, анкета и отдельный HR-кабинет. Содержит клиент, сервер, все используемые медиа, SQL-миграции и npm lock-файл. Комплект соответствует опубликованной версии 9: включает исправление непрерывного движения банок на старте. Основа: коммит dbeeefc0d667673de660c084b873ca28fe932857. Описание серверных возможностей и проверок — в docs/RELEASE-V8.md.

**Текущий режим:** анкеты действительно сохраняются на сервере и доступны в HR-кабинете. Отправка почтовых уведомлений отключена по решению владельца: `APPLICATION_DELIVERY=cabinet`. Экран «Заявка отправлена» появляется только после подтверждения записи сервером. Адрес rabota@ochakovo.ru указан как контакт отдела подбора; письмо туда не отправляется. HR поддерживает Excel-выгрузку всех, отфильтрованных и отдельных заявок.

## Загрузка в свой репозиторий

В архиве — готовая папка проекта. Загрузите **содержимое папки** в корень своего репозитория: README.md, package.json, папки app, public, lib и остальные файлы. Сам ZIP загружать в репозиторий не нужно.

Для нового пустого репозитория через терминал:

~~~sh
git init
git branch -M main
git add .
git commit -m "Первая смена: исходный проект"
git remote add origin <URL_ВАШЕГО_GITHUB_РЕПОЗИТОРИЯ>
git push -u origin main
~~~

Вместо <URL_ВАШЕГО_GITHUB_РЕПОЗИТОРИЯ> укажите HTTPS или SSH URL своего репозитория. Если репозиторий уже содержит файлы, сначала клонируйте его и скопируйте проект в рабочую папку; не используйте принудительный push. Для загрузки из файлового менеджера включите показ скрытых файлов: .env.example, .gitignore, .gitattributes, .nvmrc, .npmrc и .openai/hosting.json нужны в репозитории. Git-команды выше добавляют их автоматически.

Из комплекта исключены история Git, рабочие базы, анкеты, секреты, node_modules, результаты сборки и временные файлы. Файл .openai/hosting.json содержит только декларации DB/R2, без идентификатора опубликованного сайта; копия не привязана к управлению текущей публикацией. В wrangler.portable.jsonc оставлен явно обозначенный локальный идентификатор БД, который нужно заменить своим перед удалённым развёртыванием.

**GitHub хранит исходники.** Для работы серверной анкеты и HR требуется серверный хостинг Cloudflare Workers + D1; GitHub Pages не запускает эти серверные методы. Порядок независимого развёртывания приведён ниже.

## 1. Установка и локальный запуск

Нужны Node.js 22.13 или новее (проверено на Node 24.22.1), npm и интернет для первой установки. Нативные зависимости esbuild/workerd устанавливаются из npm. Проверки выполнены в Linux.

```sh
npm ci
cp .env.example .dev.vars
npm run db:migrate:local
npm run dev
```

В `.dev.vars` задайте собственный случайный `HR_PASSWORD_PEPPER` (не менее 32 символов), текст и версию согласия, `APPLICATIONS_ENABLED=true` и `APPLICATION_DELIVERY=cabinet`. Почтовые ключи для этого режима не нужны. `.env.example` — только образец: Worker при локальной работе читает именно `.dev.vars`. Для проверки игры достаточно оставить `APPLICATIONS_ENABLED=false`. Порт локальной разработки по умолчанию — 5173; точный адрес напечатает команда запуска. Прогресс и черновик хранятся отдельно для каждого origin браузера.

Для случайного секрета можно использовать:

```sh
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Первый вход: откройте `/team`, введите логин `HR` и первоначальный пароль `HR`. Дополнительный ключ настройки не требуется. До доступа к анкетам обязательно задайте новый пароль длиной 12–128 символов, указав текущий. После смены пароль `HR` больше не действует. Выполните первоначальную настройку сразу после публикации. Для последующей смены нужен текущий пароль. Не меняйте pepper без процедуры сброса пароля: это сделает существующий хеш непроверяемым.

```sh
npm test
npx tsc --noEmit
npm run build
npm start
```

`npm start` запускает собранный Worker локально через Wrangler. Миграции применяются последовательно один раз; не запускайте SQL вручную повторно. Локальная база находится в `.wrangler/state/`, серверная — в D1 вашего хостинга. В репозиторий базы и анкеты не включены.

## 2. Сборка и размещение на другом хостинге

```sh
npm ci
npm run build
```

Результат: `dist/client/` (браузерные файлы) и `dist/server/` (Worker, серверные маршруты). Это приложение с сервером: копирование только HTML на статический хостинг не обеспечит приём заявок и HR.

Поддерживаемый перенос без переписывания сервера — в собственный Cloudflare Workers + D1, независимо от ChatGPT Sites:

1. Авторизуйтесь своим аккаунтом: `npx wrangler login`.
2. Создайте БД: `npx wrangler d1 create ochakovo-pervaya-smena`.
3. В `wrangler.portable.jsonc` замените `database_id` на возвращённый идентификатор, при необходимости измените имя Worker и базы. Идентификатор-заглушка для публикации не подходит.
4. Примените структуру: `npx wrangler d1 migrations apply DB --remote --config wrangler.portable.jsonc`.
5. Установите значения из `.env.example` через `npx wrangler secret put ИМЯ --config wrangler.portable.jsonc`. Сначала оставьте `APPLICATIONS_ENABLED=false`.
6. Выполните `npm run deploy:cloudflare`, настройте собственный домен/HTTPS, завершите первоначальную настройку HR.
7. После настройки БД, серверного секрета и согласия установите `APPLICATIONS_ENABLED=true`, `APPLICATION_DELIVERY=cabinet` и опубликуйте конфигурацию. Для режима без почты больше ничего подключать не нужно.

Не переносите `.dev.vars`, приватные базы и данные пользователей вместе с кодом. Для другого серверного рантайма потребуется адаптация `cloudflare:workers`, D1 и сборки Vinext; универсального Node/Express-сервера здесь нет. `wrangler.portable.jsonc` предназначен для собственной публикации; `.openai/hosting.json` сохраняет необходимые сборке декларации хранилищ, но не идентификатор исходного Site.

## 3. Внешние сервисы и ресурсы

- Cloudflare Workers: сервер; D1 (binding `DB`): постоянное хранение. На текущем сайте их предоставляет Sites. Для независимого размещения создайте свои ресурсы.
- Необязательный Resend HTTP API (сейчас выключен): уведомления на фиксированный адрес `rabota@ochakovo.ru`. Нужны API-ключ и разрешённый/подтверждённый отправитель `MAIL_FROM`. SMTP-пароли не используются: текущий рантайм Sites не поддерживает произвольное TCP SMTP-соединение. Все ключи находятся только на сервере.
- Npm registry нужен при установке зависимостей; lock-файл включён.
- Все изображения Риты, фоновые иллюстрации, фотографии, три видеоролика и VTT-сопровождение находятся в `public/assets/`. Карта, упаковки и часть иконок — локальные SVG в JS. Звуки синтезируются Web Audio, внешних аудиофайлов нет. Справочник учебных заведений — `public/education.js`; это курируемый небольшой список с ручным вводом, не полный реестр РФ.
- Внешние ссылки на официальный сайт и источники справочника — справочные переходы, не обязательные загрузки. Внешние CSS, изображения, видео или веб-шрифты в игровом процессе не требуются. Используются системные Tahoma/Arial/Trebuchet; лицензированных файлов Proxima Nova в исходном проекте нет, они не выдуманы и не включены.
- Встроенная инфраструктура Sites/ChatGPT-коннекторов сохранена для совместимости сборки; HR использует собственные серверные сессии и не требует ChatGPT-аккаунта.

Качество банки сверено с официальными материалами. Доступного фото-референса 0,5 л в полученных вложениях не оказалось; официальный каталог показывает 0,45 л. Поэтому объём на игровой иллюстрации не указан. Это ограничение исходных материалов, а не утверждение об утверждённой упаковке 0,5 л. Источники: `docs/PRODUCT-ART-V7.md`. Исходники иллюстраций — `art-source/`.

## 4. Где находятся анкеты и как отправляются письма

До подачи черновик и игровой прогресс хранятся в localStorage текущего браузера (`ochakovo-first-shift-v3`). Это не серверная заявка. Приём работает при наличии D1 и обязательных переменных: флаг включения, текст и версия согласия, серверный секрет HR. Первоначальная настройка HR и почтовые ключи не блокируют сохранение анкеты.

После серверной проверки `POST /api/applications` атомарно записывает заявку в D1 `applications`, событие в `events` и задание уведомления в `mail_outbox`. UUID `submission_key` уникален: повтор одного запроса возвращает прежнюю заявку. Изменённые данные с тем же ключом получают 409, не перезаписывая ранее принятую заявку. Повторные нажатия заблокированы на клиенте; серверная идемпотентность работает независимо от браузера.

В текущем режиме создаётся запись уведомления со статусом `cabinet`: заявка принята в HR-кабинет, отправка почты для неё не планируется. Эти записи не отправятся автоматически даже при будущем подключении почты.

Только в режиме `APPLICATION_DELIVERY=email`, при настроенных ключе и отправителе, после сохранения сервер передаёт письмо Resend. В письме: ФИО, выбранный способ связи и контакт, дата рождения, учебное заведение, направление, готовность, дата/UUID, версия согласия и категории источника/места открытия. Получатель жёстко задан на сервере, посетитель его изменить не может.

Статусы `mail_outbox`: `cabinet` — принята в кабинет, без почтового уведомления; `pending` — ожидает; `sending` — передача; `accepted` — сервис подтвердил принятие с ID; `failed` — явный отказ; `unknown` — исход не подтверждён; `needs_review` — требуется ручная проверка. **Принятие сервисом не подтверждает доставку или прочтение HR.** Webhook доставки не подключён.

При сбое заявка остаётся в D1. HR видит статус, число попыток, ID сервиса и может повторить отправку; действует пауза с нарастанием, блокировка конкурентных попыток и ключ идемпотентности провайдера. Автоматического cron-повтора нет. Неопределённый исход спустя 23 часа переводится на ручную проверку, чтобы не переслать письмо повторно после истечения окна идемпотентности. Проверка почты выполнялась перехватчиком HTTP; вымышленные анкеты компании не отправлялись.

HR-пароли хранятся хешами (PBKDF2-SHA256 100 000 итераций, случайная соль, HMAC с отдельным серверным pepper). Сессия: случайный токен, в БД только его SHA-256, cookie HttpOnly/SameSite=Strict/Secure на HTTPS, срок 8 часов. Смена пароля и выход аннулируют сессии. API списков, подробностей, Excel-выгрузки, аналитики и повтора отправки проверяют сессию и завершение смены пароля. Есть same-origin проверка записей, лимит входа/смены пароля (8 за 10 минут), лимит заявок (15 за 10 минут/IP), honeypot и ограничение размера тела.

Схема: `db/schema.ts`; применяемые миграции: `drizzle/`. Таблицы: `applications`, `mail_outbox`, `hr_users`, `hr_sessions`, `hr_login_limits`, `intake_limits`, `events`. Аналитика не содержит полей анкеты. Реальные анкеты не включены в репозиторий. Резервное копирование, сроки хранения, удаление и доступ сотрудников должен настроить ответственный владелец эксплуатации.

## 5. HR и Excel

Кабинет `/team` рассчитан на десктоп: поиск по ФИО, контакту и учебному заведению, фильтр направления, подробная карточка. Кнопка «Скачать все · Excel» выгружает все заявки независимо от фильтра. «Скачать выборку» учитывает поиск и направление. В строке и карточке есть отдельная выгрузка одной заявки. Список подгружается порциями по 50; это не ограничивает экспорт. Один файл ограничен 10 000 заявок: при превышении сервер явно просит сузить фильтр и не отдаёт незаметно обрезанный список.

Файлы `.xlsx` формируются на сервере библиотекой fflate без передачи анкет стороннему сервису. В них 15 столбцов, включая UUID, московское время подачи, поля анкеты и статус уведомления. Телефоны, даты рождения и идентификаторы записаны текстом. Формулы из пользовательского ввода не исполняются. Файлы передаются только после проверки сессии, с `Cache-Control: private, no-store`.

## 6. Настройки новой установки

На исходном опубликованном сайте включён приём в кабинет. В новой установке нужно создать свою D1, задать параметры из .env.example и выполнить первый вход HR/HR с обязательной сменой пароля. Производственные настройки, учётная запись HR и анкеты в этот комплект не переносятся.

Почтовая отправка по запросу владельца отключена. Для её будущего включения нужны `RESEND_API_KEY`, подтверждённый `MAIL_FROM`, `MAIL_PROVIDER=resend` и `APPLICATION_DELIVERY=email`; проверять на отдельном тестовом ящике. Для адреса без суффикса аккаунта Sites нужен собственный домен и доступ к его DNS. Простая смена slug меняет только начало адреса.

Условия вакансий и правило 18+ сохранены из предыдущей версии; новых возрастных ограничений не добавлено.

## Структура

`app/` — оболочка и API; `public/` — страницы игры, компоненты, логика, стили и материалы; `lib/` — серверная проверка, авторизация, почта; `db/`, `drizzle/` — структура БД; `tests/` — проверки без отправки реальной почты; `scripts/` — установка/сборка; `docs/` — источники и отчёты. Старые документы V5/V6 сохраняют историю; при расхождении актуален этот README и `docs/RELEASE-V8.md`.
